# 과제별 구현 설명

## 원칙

- 기존 함수를 최대한 재활용했습니다.
- 새 함수가 필요하면 기존 함수의 네이밍과 역할 범위를 참고했습니다.
- 경계 데이터나 라이프사이클 쪽은 예외 상황부터 확인했습니다.

## 1. DTO — `naver_stock_dtos.dart`

`fromJson`은 전부 `_readString`/`_readDouble`/`_readInt`/`_readLocalDate`만 거쳐서 값을 읽게 했고, 호출부마다 `context: '$context.필드명'`을 넘기도록 만들었습니다([naver_stock_dtos.dart:181-184](lib/features/watchlist/data/dtos/naver_stock_dtos.dart#L181-L184)).

필드가 DTO 하나당 20개 가까이 됩니다. `context` 없이 `FormatException`만 던지면 어떤 DTO의 어떤 필드에서 터졌는지 메시지만 보고는 알 수가 없어서 넣었습니다.

## 2. Client — `naver_domestic_stock_client.dart`

실시간 시세(`fetchRealtimeQuotes`)는 여러 심볼을 `SERVICE_ITEM:005930,000660` 형태로 한 요청에 묶어서 보냅니다([naver_domestic_stock_client.dart:146-148](lib/features/watchlist/data/clients/naver_domestic_stock_client.dart#L146-L148)). API 자체가 이렇게 여러 심볼을 받도록 설계돼 있어서, 굳이 나눠 보낼 이유가 없었습니다.

일별시세는 JSON이 아니라 HTML이고 심볼+페이지 단위로만 요청할 수 있어서 이렇게 묶을 수가 없었습니다. 그래서 `package:html`로 DOM을 파싱하고 `querySelectorAll('table.type2 tr')`로 row 단위로 순회하도록 짰습니다([naver_domestic_stock_client.dart:247-253](lib/features/watchlist/data/clients/naver_domestic_stock_client.dart#L247-L253)). 정규식으로 문자열을 직접 긁는 방법도 있었지만, `<td>` 안에 `<span>`/`<img>` 같은 스타일 태그가 섞여 있어서 그것까지 하나하나 걷어내야 하고 마크업이 조금만 바뀌어도 깨지기 쉽습니다. DOM으로 파싱하면 `.text`만 읽어도 태그가 자동으로 걷어지고, row/column 구조도 트리로 다뤄서 더 안정적이라고 판단했습니다.

동시 실행 개수는 4개로 제한했습니다(`_runInBatches`, `dailyHistoryFetchBatchSize`). 다 병렬로 쏘면 더 빠르지만, 짧은 시간에 요청이 몰리면 스크래핑 패턴으로 감지돼 레이트 리밋이나 IP 차단을 당할 위험이 있어서 일부러 끊었습니다. 실시간 시세 배칭은 효율 때문이고 이건 차단 회피 때문이라, 같은 "배치"라도 이유가 다릅니다.

`fetchRealtimeQuotes`는 quote 하나가 파싱에 실패하면 배치 전체(다른 심볼들까지)가 같이 죽는 구조였습니다. `searchStocks`엔 이미 개별 row를 건너뛰는 처리가 있었는데 여긴 빠져 있었습니다. `_parseHistoricalPriceRow`가 쓰던 "실패하면 null을 반환하고 `.whereType<...>()`으로 걸러내는" 패턴을 그대로 가져와 고쳤습니다(`_parseRealtimeQuoteItem`, [naver_domestic_stock_client.dart:190-202](lib/features/watchlist/data/clients/naver_domestic_stock_client.dart#L190-L202)). try/catch를 루프 안에 바로 넣지 않은 이유는, 파싱하는 로직과 순회하는 로직을 분리하고 싶었고 이미 검증된 패턴이 있는데 새 패턴을 하나 더 만들 이유가 없었기 때문입니다.

## 3. Repository — `naver_watchlist_repository.dart`

`fetchWatchlist`([naver_watchlist_repository.dart:43-168](lib/features/watchlist/data/repositories/naver_watchlist_repository.dart#L43-L168))가 원래 길었습니다. README가 준 흐름(즐겨찾기 로드 → 심볼 변환 → 메타데이터/실시간 로드 → historical 조회 → 매핑)을 번호 주석으로 그대로 남겨뒀습니다. 함수를 잘게 쪼개는 대신 주석으로 단계만 나눈 이유는, 각 단계가 앞 단계의 중간 결과를 그대로 이어받는 선형 흐름이라 억지로 쪼개면 파라미터만 늘고 오히려 읽기 어려워졌기 때문입니다.

메타데이터·실시간 시세·거래일 목록은 서로 기다릴 필요가 없어서 `.wait`으로 한 번에 실행하게 했습니다([naver_watchlist_repository.dart:119-123](lib/features/watchlist/data/repositories/naver_watchlist_repository.dart#L119-L123)). `_runInBatches`(batchSize 4)로 동시 요청 개수를 제한한 이유는 Client와 같습니다 — 차단 회피입니다.

## 4. Widget / 상태 동기화

즐겨찾기 상태의 원본은 `favoriteIdsControllerProvider` 하나뿐입니다. 검색 결과나 하트 아이콘은 각자 상태를 따로 들고 있지 않고 항상 거기 구독해서 파생시키게 만들었습니다 — 따로 들고 있으면 두 상태가 어긋날 수 있어서입니다.

토스트는 2초 뒤 자동으로 사라지고(`Timer`), 새 토스트가 뜨면 이전 타이머부터 취소합니다. 안 그러면 타이머가 계속 쌓입니다.

`SearchResultRow`/`SearchToast`는 상태 없는 `StatelessWidget`으로 만들었고, 스타일은 `AppTypography`/`AppColors` 상수에 위임했습니다.

하트 버튼은 `_pendingFavoriteToggles`(처리 중인 item id `Set`)로 따닥(더블탭)을 막았습니다([search_screen.dart:47-66](lib/features/search/presentation/screens/search_screen.dart#L47-L66)). `Set.add()`가 이미 있는 원소면 `false`를 반환하는 걸 이용해서, 처리 중인 아이템이면 새 탭을 무시하고 `finally`에서 제거하도록 했습니다. 막지 않으면 즐겨찾기 저장이 두 번 나가고 관심종목 새로고침(`watchlistControllerProvider.refresh()`)도 두 번 나갑니다.

날짜 바텀시트는 연도를 바꾸면 그 연도에 없는 월/일이 남아있을 수 있어서, 필요할 때만 월/일 휠을 다시 맞추게 했습니다(`_scheduleWheelSync`). 바로 안 하고 `addPostFrameCallback`으로 미룬 이유는, 아직 빌드 중인 프레임에서 컨트롤러를 건드리면 안 되기 때문입니다.
